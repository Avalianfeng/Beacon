# 06 brief 注入架构：耦合点盘点与模块化改造评估

> **任务**：站在 01–04 四份探查结论之上，评估 brief 的调用与注入是否值得改造为更模块化（方便使用/组合/维护、不写死代码、更有扩展性）。本文**只做架构评估不实现**；行号基于当日工作区；「建议/推测」均显式标注。
> **结论一句话**：值得做**最小声明式收敛（方案 A）**——把「节点 → 字段子集 → 渲染器」收敛成一张表；不值得做注册制（B）与一等输入对象管线（C）。驱动判断的三条项目现状：schema v1 冻结、M3 已拍板不排期、操作面主路径下 S9 部分节点使用率低（ACT-01 coder 重估）。

## 一、现状耦合点盘点

### CP1 节点 → 渲染器映射散落在 6 个 prompts 文件（每处都是「if brief is not None + 局部 import + 拼块」三件套）

| 注入点 | 位置 | 渲染器 |

| prompts/blueprint_critic.py:31-34 | 同款三件套 | render_full_brief |
| prompts/coder_figure_one.py:143-146 | 同款三件套 | render_coder_brief |

- **为什么这是耦合**：6 个 prompt 文件各自手写「import 哪个渲染器 + 拼到哪个位置」，节点↔渲染器的对应关系只存在于这些分散的 import 语句里，没有一处集中声明；新增一个消费节点（如 paper_critic 收 scoring_notes）要手改 3 处：nodes/paper_critic.py（给 build_prompt 加 brief 参数）、prompts/paper_critic.py（import + 调用 + 拼接）、brief.py（新渲染器或扩展现有）。
- **新增消费节点/消费字段的改动处数**：3–4 处，全手工，且漏一处不报错（静默不注入）。

### CP4 state 与 brief 的耦合（当前属可接受现状）

- state.py:313-314 `brief: ModelingBrief | None = None`（state.py:17 import ModelingBrief）；下游 5 节点从 state 取对象注入。
- **为什么这是（轻）耦合**：建模 Brief 作为 pydantic 对象进 state，checkpoint 序列化/恢复依赖它；但「哪个节点用哪块」的决定不在这里而在 CP1 的 6 个 prompts 文件——**state 层只承载对象，注入选择权完全下沉到散落点**。对象进 state 本身是正常做法，不构成改造理由。

### CP5 门禁与渲染共用字段清单但语义不同（reference_direction 盲区的结构根源）

- `_BRIEF_ITEM_FIELDS`（brief.py:74-82）同时是门禁 id 来源（brief.py:163-172）与 CLI 统计口径（cli.py:2239-2241）；reference_direction（list[str] 无 id）不在其中 → 门禁不覆盖文献方向（04 报告 §3.4 盲区）。
- **为什么这是耦合**：若未来要「reference_direction 进门禁」，改 `_BRIEF_ITEM_FIELDS` 一处即可（id 收集逻辑通用）；但渲染层 render_full_brief（brief.py:256-258）已有独立手写块，两处要同步理解才能对齐「哪些字段是条目型/哪些是纯文本」——类型语义没有一处集中表达。

### CP6 CLI 双轨加载 brief（严格 vs 宽松路径）

- 严格路径：cli.py:328-335 `_load_brief_or_raise`（schema 校验，run/supervise/start 用）。
- 宽松路径：cli.py:1065-1078 `_load_paper_brief`（仅 JSON 可解析 + 顶层 dict，S6 用），字段名硬编码在 cli.py:1112（"required_discussions"）、cli.py:1143（"per_question_direction"）与 paper_expand.py:197-207。
- **为什么这是耦合**：同一份 brief 在 S9 走 pydantic 模型、在 S6 走裸 dict + 字符串键——「字段名/结构」的事实源分裂成两套；若 schema 升级（如新增字段）S6 侧要独立跟进。

## 二、模块化改造候选方案

### 方案 A（轻）：声明式映射表 `NODE_BRIEF_SLICE`

在 brief.py 集中一张表：节点名 → 字段子集，渲染器收敛为一个通用纯函数 `render_slice(brief, fields)`（含保留现有输出格式的分块排版）；6 个 prompts 只查表不手写 import。

```python
NODE_BRIEF_SLICE: dict[str, tuple[str, ...]] = {
    "analyst": _ALL_FIELDS, "blueprint_critic": _ALL_FIELDS,
    "modeler": ("per_question_direction", "formula_notes", "_dimension"),
    "coder": ("red_lines", "formula_notes", "_dimension"),
    "model_critic": ("formula_notes", "red_lines"),
    "writer_section": ("required_discussions",),   # 保留分组过滤参数
}
```

- **改哪些文件**：brief.py（新增表 + `render_slice`；现有 5 个渲染器改为薄包装或直接删除后由 prompts 改调 `render_slice(brief, NODE_BRIEF_SLICE[node])`）、6 个 prompts 文件（import 行收敛）。nodes/ 不动。
- **兼容性**：渲染输出逐字符不变（`render_slice` 复用现有块排版）→ `tests/test_brief.py:5-20` 的渲染器断言零破坏（若保留薄包装则连 import 都不动）；无 brief 恒通过语义不变（渲染器 None 早退、门禁 brief.py:179-181 None 早退均保留）。
- **成本/风险/收益**：成本低（约 1 天含测试）；风险低（纯收敛、无行为变化）；收益 = 新增消费节点只加表一行 + node 传参一处；新增消费字段只改表 + 渲染块一次；6 处散落 import 消失。
- **局限**：不解决 CP3（check 聚合）与 CP6（S6 双轨），需要配合小改（见 §三①）。

### 方案 B（中）：注册制 / 装饰器

渲染器注册 + 字段子集声明随注册走：`@brief_slice(node="coder", fields=(...))` 装饰渲染函数，prompts 从注册表取。

- **改哪些文件**：brief.py（注册表 + 装饰器）、prompts 6 处（改查注册表）、新增 registry 模块。
- **兼容性**：渲染输出不变 → 单测兼容；但装饰器引入导入顺序依赖与隐式注册（IDE 跳转/静态分析变差）。
- **成本/风险/收益**：成本中；风险中（隐式行为）；收益与 A 相同——**本项目注入点只有 6 个、且节点数增长缓慢（S9 还在被 ACT-01 重估是否收缩），注册制的灵活度用不上**，属于为扩展性预支复杂度。

### 方案 C（重）：brief 作为一等输入对象 + 统一 prompt builder 管线

brief 贯穿 state/prompt 构建器：收敛 6 个 `build_prompt` 签名为统一 builder 注册管线，节点只声明需求字段（配合 A 的表驱动 + 渲染管线化）。

- **改哪些文件**：6 个 prompts 的 build_prompt 签名 + nodes 传参 + graph + state + 全部相关测试（test_graph_gate、test_brief、test_cli 等）。
- **兼容性**：**高风险**——动了主路径签名，必须全量回归「无 brief 恒通过」语义（routing.py:25-33、brief.py:179-181 早退是既有硬约定）。
- **成本/风险/收益**：成本高（数天）；收益最大（background_knowledge/redline_rules 未来注入点、evaluation 接线、S7 校验器接入都会更顺）——但**与项目现状错配**：schema v1 冻结（brief.py:110-112）、M3 已拍板不排期、三字段（background_knowledge/redline_rules/comparison_baselines）何时落地未定、S9 节点使用率本身在被重估。为「可能长期不落地的扩展性」重构主路径，ROI 差。

## 四、结论：值得不值得、推哪个

**值得做，但只做方案 A（或 A−：只加 `NODE_BRIEF_SLICE` 表 + `render_slice`，保留旧渲染器薄包装）。**

判据（基于证据，非感觉）：

1. **耦合点数**：真耦合 2 处（CP1 六文件散落、CP2 三清单漂移+渲染循环双写），伪耦合 4 处（CP3 写死但低频——4 个 check 工具长期未增；CP4/CP5/CP6 属可接受现状）。真耦合的每次成本是「4–6 处手改且漏改静默」。
2. **改动频率**：低-中频——schema v1 冻结、M3 不排期、三字段未落地；队列中只有 ACT-03（节点×brief 覆盖矩阵）与 ACT-08（background_knowledge 注入）两个字段级动作。**频率低意味着方案 B/C 的「扩展性溢价」无法兑现**。
3. **风险约束**：改造不得破坏「无 brief 恒通过」（routing.py:25-33、brief.py:179-181 早退）与产物格式（steps/、checkpoints.sqlite）——只有方案 A 满足「渲染输出逐字符不变 + 单测零破坏」。
4. **项目现状**：操作面主路径（S0–S8）不跑 S9；S9 部分节点使用率低且 ACT-01 正在重估 coder 必要性——**对一条可能收缩的路径做重型架构投资，方向相反**；而方案 A 的低成本收敛即便 S9 收缩也不浪费（表本身是文档价值）。

**推荐方案 A + 两个顺手小改**：① 方案 A 落地时把 CP3 的 `_CHECK_NAMES` 一并声明化（为缺口①铺路，成本半天）；② 缺口③（`_jsonable`）独立修复，与 A 无关但成本极低、可审计性收益确定（已实测污染 3 个字段）。**不推荐** B（隐式注册换不来 6 个注入点场景下的收益）、**明确不推荐** C（与 ACT-01/M3 现状错配，且触碰「无 brief 恒通过」的兼容红线）。

**兼容语义清单（任何方案都必须保留）**：`brief is None` 时渲染器返回 ""（brief.py:208-209,273-274,295-296,314-315,345-346 五处早退）；门禁 None 早退（brief.py:179-181）；schema_version=1 硬门（brief.py:110-112）；CLI 统计口径（cli.py:2239-2241）与 FIELD_SPECS 对齐。
