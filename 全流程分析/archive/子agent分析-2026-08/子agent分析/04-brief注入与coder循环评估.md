# brief 注入与 coder 循环评估（worker · 2026-08-28）

## A. brief 注入机制

- **裁剪注入本身合理**：各节点只需对应约束子集，全量注入稀释注意力；brief_coverage 门禁放在 blueprint 阶段也对——蓝图是唯一必须覆盖全 51 条的产物。
- **根因 =「约束只有一种形态：文本」**：注入 ≠ 约束。机器校验只存在于 blueprint 一站，其余各站全靠 LLM 自觉；评分点断供、evaluation 死分支都是同一根因的暴露，不是孤立 bug。
- **方向判断**：按约束性质分级，而非按节点裁剪——红线/数据口径/评分点属**硬约束**，应落到机器校验（各站产物子集校验器）或参数传递（评分清单显式传入 evaluation）；方向/讨论点属**软约束**，文本注入足够。补一张「节点×brief 子集」覆盖矩阵即可查出断供类问题（最小改进面）。

## B. coder 循环

- **外部 agent 写代码时，LLM 循环应降级为兜底而非主力**：frozen_asset 已证明操作面产物可直接进机械装配——LLM 生成-审查链在操作面存在时是冗余层；保留价值仅在无外部实现或需快速修复时。
- **agent 迭代更有依据**：agent 闭环在真实信号上（报错=机器事实、输出可对数据对拍）；LLM 审查闭环在文本推断上（审查意见本身可能错、单视角）。现有循环信号源错位——execute 已产生真实证据，喂回的却是审查意见而非执行证据；一致性审查只证「自洽」不证「正确」。r3 阈值死区正是人为标尺脱离实际门禁的例证。
- **介入点不复杂**：天然位置 = coder_execute 之后、retry 之前——把反馈内容从「审查意见」换成「执行证据（报错/输出/对拍结果）+ 审查意见作补充」，循环骨架不用动；治理问题（何时启动 agent、会话归属）比技术问题大，但操作面已有先例，属已有流程的自动化而非新设计。

## 最值得注意的一点

A、B 是同一个根因的两面：**该用硬信号（机器校验、真实执行输出）的地方，体系在用软信号（文本注入、审查分数）**。评分点断供靠自觉、放行靠审查意见而非执行证据，都是软信号失效的实例；把「机器校验 + 真实输出」确立为约束与证据的主通道，两条线的问题同时消解。
