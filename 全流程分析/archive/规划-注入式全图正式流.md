# 规划 · 注入式全图正式流

> **已落地，不当现行用法。** 命令与交棒只看 [全流程定稿/00-正式闭环.md](../全流程定稿/00-正式闭环.md)。  
> 真跑过程：[图内真跑/案例-2026-09-05-cumcm23-c.md](../图内真跑/案例-2026-09-05-cumcm23-c.md)。`--from writer` 不是正式入口。

## 0. 一句话

正式路径从「`--from writer` 拦腰截断 + 桥接 evidence」改为「全图自然流 + `plan.json` 注入」：研究收束产出机读 plan → 播种到 analyst/modeler **产出位**（生成节点不跑）→ 图内 critic 真跑 → 过则原边流入 coder → 登记代码当参考被执行 → 本地 agent 按一致性意见改正式代码（每次改后重登记）→ sensitivity / figure / writer / paper_critic 全自然跑 → 评审证据齐 → `completed` 可达。

图的节点、边、门禁不改结构。改的是 **入口怎么把已有研究放进产出位**，以及几处「今天会静默跳过」的闸要改成真停。

## 2. 探查结论（代码事实，规划必须对着写）

### 2.1 图实际长这样（不是「analyst 之后直接 coder」）

```text
START → analyst → blueprint_critic
                 ├─ stop
                 └─ modeler（stage 默认 basic）
                      ├─ final 时还有 derivation ×6 + consistency LLM
                      └─ model_critic
                           ├─ basic/improved 过 → advance_stage → 再进 modeler
                           └─ final 过 → coder → execute → model_code_consistency
                                └─ 过 → sensitivity → figure → writer×7 → paper_critic → …
```

因此「注入蓝图就自然到 coder」是假的。必须同时做到：

1. `as_node="analyst"` 播种（跳过 analyst 生成）——机制与 writer 桥同款，现成。
2. 播种里带上 **final 模型卡**，且 `stage_target="final"`，否则会进 basic→improved→final 三档循环。
3. **`modeler_prepare` 必须短路**：`blueprint_critic` 过了之后边是死的，下一跳永远是 `modeler`。不短路就会 LLM 重写模型、final 还会跑推导链——与「全跳」相反。

推荐实现：一次播种（蓝图 + 模型卡 + `plan_injected=True` + `stage_target=final`），**不要**两段 `invoke`。边不动，只在 `modeler_prepare` 见到旗标时 `modeler_phase=done`。

### 2.2 paper_critic 结构性停机从哪来

`paper_critic` 硬查两张证明：`latest_critic("modeler")` 过门槛（默认 8 分）、`model_code_reports[-1]` 过门槛。writer 桥没跑过这两节点，所以必然打回。注入式全图流让这两节点真跑，这张黄牌的根因消失。

### 2.3 登记插座已经对，缺的是节奏文案

- `coder_prepare` 命中 T-19 冻结资产 → 零 LLM wrapper → `coder_execute`。
- `restart --from coder` 会重新 `detect_frozen_asset`，**重登记后的新哈希会被下一轮执行吃到**。
- 交棒包 `edit_code` 今天只给 `restart --from coder`，**没写** `reference add --force`。正式路径上这条命令不完整。

研究代码 = v0 参考，第一次图内执行预期可能被一致性打回。这是设计，不是事故。

### 2.4 敏感性：现成插座比口头「写进 _entry」窄

| 路径 | 今天实际 |
|---|---|
| 主求解 | 冻结命中则 **完全不读** `inject/`（`inject_asset.py` 注释写死） |
| 扫参代码 | 只读 `data_dir/inject/sensitivity.py`（即 `problems/<题>/source/inject/sensitivity.py`） |
| 缺文件且 coder LLM 关 | 节点记 error、`sensitivity_phase=done` → 路由当成功，**静默进 figure** |

落地必须改的一点：正式 `--plan` 路径上，缺扫参脚本或扫参失败 = **停机 + 交棒**，不许静默跳过。

v1 约定：扫参脚本放 `source/inject/sensitivity.py`（现成读取）。若希望「写进冻结包里的 `reference/sensitivity.py` 也算」，作为同波次小扩展，不要假装 `_entry.py` 今天会被 sensitivity 节点执行。

`sensitivity_plan` 仍会 LLM 出扫参计划（用户已接受「图仍跑该子图」）。计划与 inject 脚本对不上 → 执行失败 → 交棒改脚本。

### 2.5 图：没有 PNG 不会停

`figure_prepare` 在队列为空时 `figure_phase=done`，直接进 writer。论文会没图。正式代码迭代的完成条件之一：主方案必须产出核心证据 PNG。

### 2.6 数字双轨

| | 图外 `reference run` | 图内 `coder_execute` |
|---|---|---|
| 跑什么 | 同一份冻结 `_entry` | 同一份冻结 wrapper |
| 职责 | 冒烟、人闸落账、`review-check --strict` 对照锚 | **论文引用的数** |
| writer | 不再吃 `evidence.json` | 吃 primary `CodeArtifact.stdout` |

两边应对齐；对不齐是环境/cwd/`data_dir` bug，用严格对账暴露，不让 writer 各吃各的。

### 2.7 前置够不够

研究内容够。缺的是机读字段（对照 critic 提示词）：

| critic 要审 | 现 brief/研究资产 |
|---|---|
| 蓝图：决策变量 / 目标 / 约束 / 验证计划（含数值合理区间） | 无成文 |
| 模型：变量表 / 方程 / 目标约束映射 / 逐问覆盖→公式 | `formula_notes` 有公式，映射/覆盖没有 |
| 一致性：用验证区间查 stdout 数量级 | 无成文 |
| `brief_coverage` 逐条 | 无；命令必须从 brief 条目生成骨架，否则硬门必停 |

`apply_model_card()` 已能读 assumptions / model_versions / problem_blueprint / sensitivity_runs。plan.json **复用这套 schema**，不另发明。

## 3. 目标真实流程

```text
研究收束
  brief.json（人读手柄） + plan.json v0（plan build → 人手补）
  plan check（零 token，对照 critic 字段）
  reference add --force
  reference run / verify / recertify     ← 冒烟 + 人闸，不是论文数字源
        │
        ▼
math-agent run --problem … --brief brief.json --plan plan.json --out runs/<题>-graph
  播种 as_node=analyst：
    problem_blueprint + model_versions(stage=final) + assumptions
    stage_target=final  plan_injected=True
    brief_coverage 骨架（默认 followed）
  blueprint_critic 真跑 ── 不过 → 改 plan → 新开 run（勿 restart）
  modeler_prepare 短路（不 LLM、不推导）
  model_critic 真跑 ────── 不过 → 改 plan → 新开 run
  coder 冻结执行（研究代码 = v0）
  model_code_consistency 真跑
        └─ 不过 → critic-handoff
              agent 按模型卡改正式代码
              必做：reference add --force
              然后：restart --from coder
  sensitivity_plan（LLM）→ 执行 inject/sensitivity.py
        └─ 缺脚本/失败 → 停机交棒（禁止静默 done）
  figure（有 PNG 才审；无图空过，论文会缺图）
  writer × 7 → paper_critic（两张证明真实存在，门能真过）
  table → evaluation → 人审 → latex → finalizer（completed）
        │
        ▼
review-check --strict   图外对账：论文数字 ↔ evidence 关键数
accept
```

重启边界（保持现有不变性，并扩到 plan）：

- 改 **brief / plan** → 只能新开 run（manifest 哈希对不上）。
- 改 **代码** → `reference add --force` → `restart --from coder`（吃新冻结，不重放旧 stdout）。
- `restart --from writer` 只服务应急接桥，正式路径用不上。

## 5. 关键护栏（明确不做什么）

- 不改 analyst / modeler **提示词**；无「LLM 把研究卡改漂亮」的兜底路径。
- 不恢复默认 `coder_generate` LLM（`--allow-coder-llm` 仍只给旧无冻结场景）。
- 不把 `--from writer` 删掉；只降为应急。cumcm23-c **先不用它**。
- 不动探索 / Diff / 拍板。
- 不把 `reference run` 当论文数字源；也不删掉它。
- 实现未验收前，**不改定稿 00 当现行用法**（避免两套说明书）。

## 6. 风险

- `model_critic` 8 分门槛会打回 1–2 轮：这是接入正当性，不是失败。用 `plan check` 把一半打回前置掉。
- 全图真跑约 critic×3 + writer×7 + 敏感性 plan + 图审：单题数十分钟、数万 token。首跑会暴露全图流 + frozen + restart 的既有工程债，属预期。
- 研究代码第一次进一致性，大概率不过：agent 要按模型卡改到「图内契约」，不是把研究脚本原样塞进去交差。
- 敏感性 plan（LLM）与 inject 脚本可能不一致：交棒改脚本，不要让 plan 节点去改研究结论。
