# 新题上线流程（onboarding）设计——优先级高于机制批次

- 建立日期：2026-08-20
- 定位：**用户新战略**：先跑通「新题从 0 到 run」的真实使用流程，再纠结细致问题与测试；跑通流程本身即测试与迭代。
  本路线**优先级高于**批次 1–3 机制修复（M3/M4/注入补全），与机制批次无文件冲突（不动求解链路）。
- 背景痛点（代码级实证）：
  1. 题目注入只有 Web 一条路——`problem_ingest/`（pdf_text/vision/pipeline/garble）只被 `frontend/server.mjs` 调用，本地 CLI 无等价入口；
  2. spec 是 Web 端现场拼装（`server.mjs:913-928`，questions 甚至整段塞 background），只写进 run 目录、**不沉淀为题目资产**（`docs/problems/mcm51-a/` 只有 brief.json 无 spec.json）；
  3. 本地跑题体验差：`run/supervise` 手拼 `--problem --out --thread --brief`；brief init 空模板手填 40 条；brief 与 spec 无目录级绑定。
- 关联：中枢 H02（信息高保真传递）/H05（来源可追溯）/H07（候选方向）/H14（双轨入口）；spec v2 与批次 1 schema v2 合并升级。

---

## 一、两段式导入（用户定义，2026-08-20）

1. **第一段（外部手段 → 题目 md）**：题面 PDF/图片/手抄文本经外部手段（现有 ingest 管线：文本抽取→乱码检测→视觉回退，或人工整理）解析为**题目 md 文件**——事实层，归档不可变、记哈希。
2. **第二段（md 二次提取 → spec + 知识注入）**：
   - 背景信息 → `spec.background`；
   - 问题本身信息 → `spec.questions`（每题一条）；
   - 背景通识 + 专业 + 每题方向知识 → **brief 新字段 `background_knowledge`**（来源分级：official_standard > human > model_draft）；
   - 每题的方向选择/字段 → brief `per_question_direction`（骨架预填）。

## 二、资产目录约定

```
problems/<题号>/            # 题号交互输入（决策 3）
  source/                   # 原始题面+附件（不可变，登记 sha256）
  problem.md                # 题目 md（事实层）
  problem.json              # spec v2（解释层，人可修）
  brief.json                # 前置信息（8 字段 + background_knowledge）
```

## 三、spec v2 schema（详细设计）

- **设计原则**：题目 md=事实层（不可变）；spec=解释层（解析错误可修，不污染原文）；questions 保持字符串数组（向后兼容现有 `_read_problem_spec` 五字段）。
- **新增字段**：

```jsonc
{
  "schema_version": 2,
  "problem_id": "2026-mathorcup-b",        // 交互输入
  "title": "...",
  "background": "...",
  "questions": ["..."],
  "source": {
    "md_path": "source/problem.md",
    "source_files": [{"path": "...", "sha256": "..."}],
    "imported_at": "...",
    "imported_by": "human|cli"
  },
  "feasibility": {                          // 可达性初评（新机制）
    "checklist": ["external_data", "simulation", "survey", "supercomputer"],
    "blockers": ["需要真实机器人仿真平台"],   // 非空 → run 前强制中断
    "assessment": "..."
  },
  "data_files": [...],                     // 兼容字段保留
  "data_dir": "..."
}
```

- **兼容**：`_read_problem_spec` 对 v1（无新字段）逐字节兼容；run 只消费五字段 + feasibility.blockers 检查。

## 四、CLI 命令设计（本地一等公民）

1. **`problem import <题面文件|md> [--attachments <目录>] [--problem-id <题号>]`**
   - 归档 source/ + 记 sha256 → 解析/接收题目 md → **AI 起草 spec draft**（结构化拆 title/background/questions/feasibility 初评）→ 人工确认 → 落 `problems/<题号>/problem.json`
   - 二次提取：`problem import --extract` 续跑（md → spec 字段 + brief 骨架 + background_knowledge draft）
2. **`problem show <题号>`**：总览（spec 摘要 + 附件清单 + feasibility 状态 + brief 状态 + 最近 run 指针）
3. **`brief init --problem <problem.json>`**：按小问预填 `per_question_direction` 骨架（question_id 自动对应）、problem_id 带出（B04 匹配打底）；人工填充从骨架开始而非空白
4. **`brief check` 增强**：brief↔spec 联动（question_id 覆盖性、problem_id 匹配）
5. **`run --problem ... --brief ... --dry-run`**：spec 合法 / brief 合法 / **feasibility.blockers 非空 → 报不可达并拒绝启动** / 附件存在 / out 冲突，一次全报

## 五、可达性预检与强制中断（能力边界认识）

- 原则：**信息呈现在流程中，不内置于节点**；题目若依赖我们能力不可及的资源（真实调研、超算仿真、专用平台数据、实物实验），必须**在源头明确指出并强制中断链路**，而不是让 run 烧到中途失败。
- 落地：`problem import` 时由 AI 起草 + 人工确认 `feasibility.blockers`；`run --dry-run` 与 `supervise` 启动前检查，非空即拒绝并打印原因。
- 例：MathorCup 2026 B 题（机器人竞技策略）依赖真实机器人仿真平台/硬件参数——若无仿真数据源应标记 blocker。
- 完整形态（自动识别能力边界、前端可视化）依赖 09 的前端重设计，属长远方向；本阶段先做最小版（人工确认的 blockers）。

## 六、外部评估通道（节省 token / 人机协作）

- 原则：论文产出与自我修改体系不必完全依赖本地；**接入人的交互是极好策略**。
- 落地（低成本）：evaluation/human_review 后生成**评估简报 md**（关键结果、候选方向路径、残留疑问点、需外部判断的问题清单），随论文产物给用户；用户可自行把简报发给网页版 AI（GPT 等）做外部评估，结论回填 brief（源头修订，原则 8 合法回路）——体系内不注入自动投票。
- 完整交互形态（看板内一键收集/外部评估回填）依赖 09 前端。

## 七、里程碑与验收（A 最小闭环）

1. **M1**：`problem import`（md 接收 + spec v2 落盘 + source 归档哈希）
2. **M2**：`brief init --problem` 骨架 + `brief check` 联动
3. **M3**：`run --dry-run` 预检（含 feasibility 中断）
4. **M4**：`problem show` 总览
5. **验收**：用一道真实新题（如 MathorCup B 或任一题目 md）走通「import → brief 填充 → dry-run → run」全流程，产出与 Web 等价；跑通即测试，迭代改进。

## 八、与批次 1 schema 的合并

- spec v2 + brief `background_knowledge` + M3 `redline_rules` + M4 `comparison_baselines` → **一次 schema v2 升级**（向后兼容 + 迁移脚本或直接双版本支持），排期在 M1 之前完成 schema 设计评审。
