# M3 红线机器化 · 说明（2026-08-26）

> **用途**：回答"M3 红线机器化具体是什么"——是什么、为什么、做什么、价值与局限、以及按当前执行原则
> （贴合真实流程 / agent 侧优先 / 明确价值）的取舍建议。设计原文见 `02-批次1-机制工程A-M3红线确定性校验.md`。

---

## 一、是什么（一句话）

**M3 = 把 brief 里的"红线/禁止项"从文本变成机器可读规则，在代码/输出产物上做确定性校验，
违反即进入 修复→停止 路径——不再靠 LLM 评审"自觉"压线放行。**

- 对象：brief 的 `red_lines`（现为文本条目，如"禁止硬编码官方参考值 600.71""K_avg 不得整体使用"）。
- 位置：校验落在**产物**上（coder 产出的代码文本 + 求解 stdout），不是评审嘴上
  （H05 教训：coverage 39/39 只证明声称，校验必须落在产物）。

## 二、为什么需要（历史实证）

- **B16**：brief-v1 中 K_avg=0.1783 违反"禁整体 K 红线"，LLM 评审仍给 8 分**压线放行**——
  红线靠评审自觉，不可靠。
- 8-26 C 类补的是**评审侧**口径核查（假设依据/大 gap/溯源）；M3 补的是**执行侧**产物红线——
  两者互补，不重叠。

## 三、做什么（v1 保守实现，来自 02-批次1）

**1. brief schema 扩展（向后兼容，缺省不影响旧 brief）**：

```jsonc
{
  "redline_rules": [
    {
      "id": "rl-001",                  // 关联 brief 条目 id
      "target": "code|stdout|paper",   // 校验对象
      "rule_type": "literal_ban|expr_ban|symbol_ban|result_rule|unit_mix_ban",
      "pattern": "600.71",             // 字面量 / 正则 / 符号名 / 数值表达式
      "severity": "hard",              // hard=违反即 stop；warn=记入诊断不阻断
      "note": "禁止硬编码官方参考值"
    }
  ]
}
```

**2. rule_type 语义**：
- `literal_ban`：代码含数值字面量（含格式化变体 `600.710`、`6.0071e2`）→ 违规（最确定）；
- `expr_ban`：正则匹配（如 `0\.8\s*\*\s*T_max`）→ 违规（较确定）；
- `symbol_ban`：符号出现检测（如 `K_avg`）——v1 宁严勿松，**误报率需真跑实验观察**（合法讨论也报出）；
- `unit_mix_ban`：单位混用（kN/MPa/kN·m 同式）——warn 级先观察误报（D3 决策：M5 校验层并入）；
- `result_rule`：stdout 数值等式/区间（如 `T_opt == 0.8*T_max`）→ 违规（依赖结果解析，warn 级）。

**3. 接入**：纯函数 `redline_violations(brief, code_artifacts, stdout_lines)`（不调 LLM）→ routing
在 model_code_consistency 后叠加：hard 违规 → 首次 retry_coder → 预算耗尽 → stop；
warn → 写 `gate_diagnostics.json` 的 `redline_violations` 段（可审计）。

**4. 测试**：单测（三种 rule_type 报出/干净零报出/无 brief 恒通过）+ routing 集成（hard→retry→stop）
+ `brief check` schema 合法性。

## 四、价值与局限（客观评估）

| 维度 | 评估 |
|------|------|
| 价值 | 防"红线靠 LLM 压线"（B16 硬伤）；校验落在产物（H05）；与 8-26 C 类互补 |
| 适用面 | 只能覆盖**数值/符号/单位/正则可表达**的红线；语义型红线（如"不得声称精确解实为启发式"）机器难判，仍靠 C 类评审 |
| 轨 B 适用性 | **同样适用**：轨 B 求解 agent 写的脚本就是 code_artifacts，红线校验可对 agent 产物跑（不依赖轨 A）——按"agent 侧优先"原则，也可以把红线清单放进求解 agent 提示词自查 + 脚本校验双保险 |
| 工作量 | 完整版 ≈ 1–2 天（schema + 校验器 + routing + 测试）；**最小版**（只 literal_ban + expr_ban + result_rule warn，hard 仅数值型）≈ 0.5–1 天 |
| 不确定点 | symbol_ban/unit_mix_ban 误报率需真跑观察（02-批次1 §四已注明） |

## 五、取舍建议

按当前执行原则，两个选项：

1. **最小版 + 新题实测**（推荐）：走全流程实验前只实现 `literal_ban + expr_ban`（最确定的两种）+
   `result_rule` warn，把新题 brief 的数值型红线（如"禁硬编码参考值"）写进去，真跑观察误报；
   symbol/unit 留待实验后按数据定。
2. **暂缓，新题跑完按缺口定**：M3 不阻塞全流程；如果新题真跑中红线没有实际被违反（B16 是 brief-v1
   特例），则最小版也可以不做——先记录本说明，实验后 10 分钟决策。

> 结论：M3 **不是全流程阻塞项**；建议按选项 1 或 2 处理，由新题真跑的实际需要决定投入。
