## 一、动机与问题定义

**痛点（mcm51-b 实证）**：前置知识（认知地图/brief）是「最简单考虑 + 推演」，**未经真实代码验证**。
方向正确 ≠ 实现正确——本次流水线 4 次停机全部发生在实现层（total_cost 守卫误杀、C 名混用、效率解析失败、
RESULT 契约臆造），且参考实现交付后仍被交叉审查抓出两处隐蔽 bug（C 循环链展开与链序）。
**根因：方向信息与「已验证的实现事实」之间存在断层——认知层没有代码层背书。**

**轨 B 实践（v0.1 原型，2026-08-21）**：数据子 Agent 从解题角度运行参考实现 + 敏感性 + CPM + 证据清单，
写作子 Agent 基于证据写论文，评审子 Agent 独立验证——**零 LLM 调用完成全部数值与论文，且抓出实现 bug**。
证明：解题验证线路可行、便宜、可靠，且天然适配「强模型 + agent 应变能力」。

## 二、双线路架构总览

```
                     ┌──────────────────────────────────────────────┐
  原始题目 ────────► │ 线路 A：方向生产（brief 约束线，现有）          │
                     │ 人+强模型：探索→消化→对撞→清点 → brief.json     │
                     │ （方向级+口径级约束；playbook 协议）             │
                     └──────────────────┬────────────────────────────┘
                                        │ brief（方向约束）
                     ┌──────────────────▼────────────────────────────┐
                     │ 线路 B：解题验证（agent 解题线，本设计）         │
                     │ agent 读题→建数据模型→写代码→执行→数值验证      │
                     │ → 独立复核 → 「已验证信息包」（不写论文）        │
                     └──────────────────┬────────────────────────────┘
                                        │ 信息包注入（锚点/参考实现/验证记录）
                     ┌──────────────────▼────────────────────────────┐
                     │ 构建体系：论文生产（流水线或 skill 化写作）     │
                     │ 论文本体 = 方向约束 + 已验证信息包 + 写作规范    │
                     └──────────────────────────────────────────────┘
```

- **线路 A 定「方向与口径」**（做什么、不能做什么）；
- **线路 B 定「实现与事实」**（怎么算、算出来是什么——全部经真实代码执行验证）；
- **论文本体只做「组织与表达」**（把已验证事实按评分点组织成论文）。

## 三、解题验证线路（B 线）设计

### 3.1 职责与边界（严格）

- **只做**：读题 → 数据建模 → 写求解代码 → 执行 → 数值验证（量纲/边界/对账/敏感性/下界）→ 信息包；
- **不做**：论文写作（由构建体系完成）、方向生产（由线路 A 完成，若 B 线与 brief 冲突→回源头修订，原则 8）；
- **不注入**：官方答案/评分标准（防泄漏，原则 1）——锚点只能是「自己实现输出」级别的自证。

### 3.2 执行形态（分阶段）

- **v1（本次实践已跑通）**：子 Agent 三分离——解题 Agent（运行求解器+敏感性+CPM）、
  写作 Agent（基于信息包写论文）、评审 Agent（口径逐条审计+数值回源）；
- **v2（原型化）**：把本次流程固化为**可复用资产**（skill/脚本模板 + 子 Agent 提示词包 + 信息包 schema），
  新题直接套用；参考实现等「已验证资产」随题归档（problems/<题>/，哈希登记）；
- **v3（待设计）**：解题 agent 带**自修复迭代**（读执行报错→修代码→重跑，利用强模型应变能力）；
  与流水线 coder 的接入（信息包注入后，流水线 coder 直接复用参考实现——`data-reuse-impl` 已实践）。

### 3.3 验证标准（什么算「已验证」——本次评审 Agent 核对表的正式化）

信息包验收清单（逐条通过才算已验证）：
1. **执行成功**：求解代码 exit=0，无 NaN/Inf，无硬编码答案；
2. **口径逐条核对**：活动数/链序/隐藏结构（如循环链）/双设备语义/运输/取整/各问范围 vs brief 逐条对照；
3. **确定性复现**：两次运行输出逐字节一致；
4. **自检锚点**：关键数值与预期锚点一致（锚点来自冻结版实现自身输出，非外部答案）；
5. **下界对照**：给出 CPM 类无容量下界与差距%（诚实性证据，区分「启发式非最优」与「错误」）；
6. **独立复核**：由独立 Agent（或第二次独立运行）交叉验证——**本次两处隐蔽 bug 均由此抓出，不可省略**。

### 3.4 信息包 schema（evidence package，雏形=本次 evidence.md + sensitivity.json）

```jsonc
problems/<题号>/evidence-package.json {
  "version": 1,
  "solver": { "path": "source/reference_solver.py", "sha256": "...", "frozen_at": "..." },
  "anchors": { "Q1_makespan": 41600, "Q2_makespan": 215303, "...": "..." },   // 冻结版实现输出
  "verification": [ { "item": "活动总数=27", "pass": true, "evidence": "..." }, ... ],
  "sensitivity": { "resource": "...", "speed": "...", "budget_curve": "..." },
  "lower_bounds": { "critical_chain": "...", "gaps": {...} },
  "failures_log": [ "C 循环链展开 bug（已修复）", ... ],
  "honesty": { "heuristic_not_optimal": true, "notes": "Q2-Q4 构造式启发式非全局最优" }
}
```

## 四、融合机制（注入点）

| 注入 | 载体 | 本次实践对应 |
|---|---|---|
| 参考实现 + 冻结哈希 | problem.json source_files + data_dir 文件 | reference_solver.py（冻结 `504ecc0a8fa5c006`） |
| 自检锚点 | brief data_notes `data-anchor` | 已落地（52 条 brief） |
| 口径复用指令 | brief data_notes `data-reuse-impl` | 已落地（后续节点同口径） |
| 矛盾回源头 | brief 修订（原则 8；改 brief=全新 run 成本已知） | C 链 bug 修复后 brief 同步 |
| 防泄漏边界 | 锚点必须是「自己实现输出」，禁止外部答案 | 全程遵守 |

## 四·五 关键决策：资产复用（推荐）vs 提示词复用（现状）

**现状（轨 A，2026-08-21 实证）**：即使存在冻结参考实现，coder 仍由 LLM 生成包装代码（brief 指导 exec）——
每次 run 都是「对同一问题的多次解答」；4 次停机中 2 次纯属生成包装的随机失败（RESULT 正则臆造、C 名混用），
与参考实现无关；brief 因此不断追加防御性补丁（rl-result-format、formula-reference 的 exec 指令），
偏离「方向约束」本义。

**被否方案**：代码全文注入 prompt——仍由 LLM 处理完整代码（可改坏/截断/再臆造；16k 上限限制），治标不治本。

**推荐方案：资产直接执行接入（v2 方向，向后兼容）**
- coder 节点检测冻结资产（data_dir/reference_solver.py + 冻结哈希登记于 problem.json source_files）：
  存在 → **跳过 LLM 生成**，直接 runner 执行参考实现 → 输出契约校验（RESULT/PNG/无 NaN）→ 注册证据；
  不存在 → 现有 LLM 生成路径不变；
- sensitivity / figure 节点同机制（直接调用参考实现函数 / 复用其输出）；
- 证据链语义：资产 = 人工供给（来源分级 human）+ 冻结哈希；输出 = 真实执行产物——与证据纪律一致；
- 收益：生成薄弱环节结构性消失（2 个停机根因归零）、确定性复现、省 coder token（run1 中 coder_generate 占 10.7%）、
  brief 可瘦身（删防御性补丁回归方向本义）、B 线资产成为流水线确定性输入（双线路融合的机制载体）；
- 代价：coder 语义从「生成者」变「执行者」（实现+测试约 1–2 天，plan 11 量级）；图样式沿用资产（图质量另案）；
- 决策状态：**待用户确认** → 原型化（v2）。

## 五、与现有体系的关系

- **A 路线（专家副驾驶）的实现细化**：方向=人+强模型（A 线），实现事实=agent 解题（B 线），论文=体系——
  三者分离即「副驾驶」分工的正式化；
- **16 阶段 2/3 的输入**：B 线产出的已验证方法/求解器 = 方法能力库（阶段 3）的候选素材；
  信息包账本化 = 主张-证据系统（阶段 2）的雏形；
- **C 路线候选**：若 A/B 对比显示构建体系可收缩为「信息包→论文」的写作+校验 skill，
  则 B 线 + skill 化写作 = C 路线的具体形态（07 19a 待决）。

## 六、关键设计问题清单（待讨论，不阻塞原型化）

1. B 线 agent 形态：子 Agent 流程（v1 已实践）vs 专用 CLI/skill（v2）vs 带自修复迭代（v3）？
2. 验证标准阈值：口径核对项清单固定化？下界差距容忍度？什么情况必须上精确求解器（CP-SAT）？
3. 成本控制：B 线 agent 发散如何约束（限定验证范围、禁止写论文、迭代上限）？
4. 何时启用 B 线：复杂/多隐藏结构题必走；简单/标准题是否直接走构建线？（按题型分级）
5. 自修复迭代的边界：agent 修代码到何种程度可信？是否仍需独立复核兜底？（本次教训：必须）
6. B 线信息包与流水线节点（sensitivity/figure）的复用接口：直接 import 参考实现 vs 读信息包？
7. 论文写作侧：写作规范「借鉴现有写作体系」（writer 模板/critic 循环）如何 skill 化——单独立项。

## 七、风险与边界

- **B 线自身也会错**：必须独立复核（本次两 bug 实证）；验证标准不能只信 agent 自报；
- **注入 ≠ 答案注入**：锚点/参考实现是自证事实，防泄漏纪律不变；
- **启发式非最优的诚实标注**：信息包必须携带（分数视角：诚实 > 虚假最优）；
- **成本**：B 线单题成本远低于流水线重跑（本次轨 B 零 LLM 调用），但 agent 发散会侵蚀优势——用边界约束。

## 八、原型化路线

1. **固化本次流程为资产**（v2）：把轨 B 的数据/写作/评审提示词 + evidence schema 沉淀为可复用
   skill/模板（放 docs 或 scripts），第一道题原型已具备；
2. **新题验证**：选一道新干净题，A 线（brief）+ B 线（解题验证）完整跑通，对比「仅 A 线」成本/质量；
3. **与轨 A 对比收口**（07 19a）：三轨数据齐后定体系形态（A 线+B 线+流水线 vs A 线+B 线+skill 写作）；
4. **逐步产品化**：B 线 CLI（problem verify）、信息包 schema 版本化、参考实现冻结流程制度化。
