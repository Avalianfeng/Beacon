### 批次 3：求解启动 + 主会话交叉核验抓到 Q1 bug

- 3 个求解子 agent 并行（Q1+Q2 / Q3 / Q4+Q5，纯 numpy/scipy，B 类五条）。

## 批次 4：流程操作经验沉淀（可复用 / 可迭代，供后续流程迭代规划）

> 记录本会话实际执行中暴露的**操作层经验**（非建模结论、非体系决策正文）。目标是让"主会话统一管理 + 子 agent 分工"这套流程下次可复制、并知道哪里要优化。

### 4.1 子 agent 分工与产物回流的操作要点

- **分组粒度**：求解按"小问"分 3 个并行子 agent（Q1+Q2 / Q3 / Q4+Q5），依据是"方法族相近 + 无跨组硬依赖"。Q2 的阶段划分被 Q4/Q5 复用，但 brief 已写清方法，各组可独立自实现（轻微重复换取并行）。
- **产物目录约定**：每子 agent 固定工作目录 `runs/<题号>-skill-v1/solve/<分组>/`，脚本 + 输出 + evidence.md 同目录，主会话按目录汇总。**这是回流的锚点，必须事先在 prompt 里写死路径**。
- **prompt 必须自包含**：子 agent 看不到主会话上下文，prompt 要一次性给全——必读文件路径、数据路径、B 类五条、环境约束（只许哪些库）、RESULT 行格式、evidence 格式、sha256 登记要求。本次 Q3 子 agent 的 evidence 质量高，正是因为 prompt 把 B 类五条写得很具体。

### 4.2 主会话交叉核验（抓到 Q1 bug 的关键机制，强烈建议保留）

- **做法**：主会话**不信任子 agent 自报的"整模型指标"**，而是用**独立锚点**核验关键交付表。锚点来源：数据画像 F1（表1.1 的 5 个 B 同刻读数）、粗划节点（Q2 ~8000/~9600）、相关矩阵（Q3 0.898 等）。
- **实证**：Q1 子 agent 整模型 rmse=2mm（自报"好"），但表 1.1 四点偏离 B 达 26–184mm——只有用 B 同刻读数锚点核验才能发现。**教训：交付表逐格核验，不能只看汇总指标。**
- **改进方向**：可把"独立锚点核验交付表"做成主会话的固定动作清单（每问的锚点预先登记在 brief/data_notes），未来甚至可脚本化。

### 4.3 子 agent 反模式与对策（本次实测到的三类）

| 反模式 | 表现 | 对策（本次） | 改进方向 |
|--------|------|-------------|----------|
| **polish 循环** | Q1+Q2 子 agent 反复重跑同一 buggy Q1、只改图不改数，数分钟不推进 | 主会话监控"文件时间戳 + 关键值不变"，判定循环后 `interrupt_agent` 中断 | 可在 prompt 里加"每问最多重跑 N 次"或"数字未变禁止重复出图" |
| **抵抗返工** | 子 agent 在 evidence 里为 bug 辩护（"不同参数化"），不主动改 | `interrupt_agent` 中断 + `send_message` 重发**明确、带数值判据**的返工指令（"β1 应为≈1、表1.1 偏差 26–184mm 不可接受"） | 返工指令必须带"验收判据"（期望的数值范围），让子 agent 无法模糊化 |
| **stale 中间文件** | Q3 子 agent refine 后 q3_table3_1.csv 一度是旧值（1768/7/9/61），后才更新到 513/131/114/251 | 主会话**以子 agent 最终报告为准，不核验中间文件**；发现表间不一致先标记"评审必查"而非当场判定 | 子 agent 收尾时应自检"输出文件与报告一致"（Q3 的 evidence 已做 ALL CHECKS PASSED，可推广） |

### 4.5 数据驱动对撞的流程改进（本次最有价值的流程发现）

- **旧流程**：探索（§2.1）→ 消化（§2.5）→ 对撞（§3.1）——各家先"凭经验"列方法族。
- **新流程（GPT 第二家带出来的）**：**先把 EDA 做完 → 把 EDA 证据包喂给第二家 → 让第二家做"数据驱动的候选淘汰"（哪些方法不适合这组数据）→ 消化出认知地图**。这样对撞从"方法名 PK"升级为"数据证据淘汰"，并收敛到"决策点"而非"方法名"。
- **收益**：GPT 淘汰了贝叶斯变点/小波/GBDT（过度或依赖 sklearn），与 venv 现实一致；并给出 5 个真正决策点（漂移参数化/变点目标函数/lag 数据确定/防历史位移虚高/预警提前量）。
- **改进方向**：把"EDA 证据包"做成方向生产的固定中间产物（数据探查子 agent 直接产出可粘贴的 EDA 摘要），对撞提示词默认要求"先淘汰、后选主"。

### 4.6 等待与节奏（本次我的操作失误，记下防再犯）

- **失误**：求解子 agent 运行期间，我每 20–60 秒查一次文件（busy-polling），浪费大量 goal 轮次。
- **正确做法**：子 agent 完成会**主动发通知**，主会话只需在收到通知后一次性处理（汇总 evidence → 跑 check → 评审）。等待期间不做任何轮询。
- **教训**：goal 轮次 ≠ 必须做动作；"等通知"是合法状态。

- `check_gap_trigger`（下界 vs makespan）是调度题专用，**预测题（C 题）无 makespan**，需适配为"备选口径/预测误差差异 >15% 触发口径核查"（本次将手工适配并如实标注）。

### 批次 5：Q1 返工完成 + 一个重要 nuance（主会话处方 β1=1 被数据纠正为 0.88）

- Q1 返工最终结果：主口径 **B = 0.8817·A − 0.5245**（增益 0.88，非 1.0），表 1.1 五点偏差 **≤0.038mm**（峰值偏差 0.038 vs 自由三参数的 184mm vs β1=1 处方的 37mm）。
- **主会话返工处方"β1=1"被数据纠正**：子 agent 用 4 种方式实测 B~A 斜率 = 0.8807–0.8817 一致，证明"r=0.9996 是相关不是斜率"；β1=1 在跳变谷底点残留 5–37mm 偏差，故不选为主。L70 的"+0.0268 mm/h 漂移"是 0.12 增益差×A 增长率（0.12×0.237≈0.028）的副产物，两事实自洽。
- **教训（对 4.3"返工指令"的修正）**：返工指令的"验收判据"应指向**要消除的病灶**（"自由三参数退化、跳变点崩掉、表1.1 偏差须到个位数 mm 以下"），而**不要死定一个数值处方**（我写"必须 β1=1"是过度具体，好在子 agent 用数据纠正为 0.88）。正确写法是"约束增益为一个固定值，其值由数据实测 B~A 斜率决定"。
- 另：Q2 节点最终收敛为 **8148 / 9573**（早前 5289/8870 是未过幅度判据的中间值，子 agent 在 refine 中按"持续性+幅度"判据修正），已回到数据画像粗划锚点 ~8000/~9600 附近。

## 批次 6：论文生产环节的流程反思（用户提出，供迭代规划）

> 用户三点质疑 + 主会话判断。这是"流程设计"层讨论，不是本次题目的建模结论。

### 6.1 分段式书写 vs 单 agent 写全篇

- 单 agent 写全篇的真实代价：一个 agent 同时承载 9 条 discussion + 11 红线 + 3 份 evidence + 5 张交付表，上下文极长，**前后口径漂移风险高**（本次 writer 靠自检纠了 2 处）。
- 分段式（按 5 问分 + 摘要/假设/结论/附录各一段）可并行、每段聚焦，但引入：① 跨段叙事一致性（统一状态观总纲谁保证）② 跨段数字一致性（表在正文/附录都要对）。
- **关键**：轨 A 流水线本来就是 `writer_section` 分段写（mcm51-b 用过），轨 B 可借用；数字一致性由 `check_paper_numbers` 机械闸门兜底。
- **迭代方向**：分段 writer_section + 一个"主编"agent 拼装 + check 闸门兜底，优于单 agent 全篇。

### 6.2 写作对"实验验证"最不重要（但证据链封边不能丢）

- 对"方向对不对 / 数字对不对 / 口径有没有翻车"而言，polished prose 贡献最小，可省——这三件事由对撞、求解、check 闸门、评审负责。
- **边界**：mcm51-b 最大教训之一是"论文化造数"发生在论文阶段（表 9 凭空数字）。所以"写作不重要"成立的前提是**数字溯源闸门（check_paper_numbers）仍在**。
- **迭代方向**：验证用"最小论文"（摘要+交付表+数字+诚实声明，跳过花哨文字），交付前再精写——匹配"实验为主"定位。

### 6.3 体系"代码→论文"路径缺口

- 现状两条路：① 轨 A brief 注入 → 跑全流程（coder 生成代码，复杂题/无 sklearn 不可靠）；② 轨 B agent 写脚本 + agent 写论文（本次），全程主会话手动协调。
- mcm51-b 的 `reference_solver.py`（放 source/、pipeline coder exec）是"**写好的代码直接进题型**"的雏形，但挂在轨 A 上，轨 B 无对应机制。
- 本次轨 B 的 8 个脚本本质就是"参考实现"，只是主会话**手动**喂给 writer agent，没有"登记脚本 → 体系自动装配论文"的正式路径。
- **迭代方向（候选）**：轨 B 缺一个"参考实现登记 + 自动论文装配"中间件——把"agent 写好的脚本 + sha256"登记为题参考实现，体系据此自动做数字提取 + 表格装配 + 论文骨架（与 mcm51-b 参考实现同哲学，但当时只服务轨 A）。
